# Multimodal RAG for Soccer Match Event Retrieval

A retrieval-augmented generation (RAG) system for searching and retrieving soccer match events from player and ball tracking data. The system converts frame-level tracking information into structured events, creates event-specific semantic chunks, indexes them in a vector database, and connects retrieved events to their corresponding video timestamps.

## Data Source

The current repository uses synthetic tracking data and rendered match video generated by:

```text
src/utils/mock_data_gen.py
```

The synthetic dataset contains simulated 2D trajectories for players and the ball. This allows the complete retrieval pipeline to be demonstrated without relying on proprietary match footage.

The system is designed to accept real Game State Reconstruction (GSR) output. To use real tracking data, place the tracking file at:

```text
data/sample_tracking.json
```

and set the following option in:

```text
config/settings.yaml
```

```yaml
data_source: real
```

The parser layer is designed to normalize different tracking formats into the same internal representation used by the downstream pipeline.

## Example Queries

The Streamlit application can be tested with several types of queries.

### Specific Event Search

**Query**

> Show me when Team A crossed into the penalty box.

**Expected result**

The system retrieves the relevant box-entry event around:

```text
00:40 - 00:50
```

The video player is positioned at the beginning of the retrieved event.

### Defensive Turnover Search

**Query**

> Find turnovers or lost possession in the defensive third.

**Expected result**

The system retrieves a turnover event around:

```text
01:25 - 01:35
```

where Team A loses possession under pressure.

### Pressing Sequence Search

**Query**

> When was Team A subjected to a high pressing sequence?

**Expected result**

The system retrieves a continuous pressing sequence around:

```text
02:10 - 02:25
```

involving three or more defenders.

### Negative Query

**Query**

> Was there a second yellow card given to any player?

If the query does not have a sufficiently similar event in the vector store, the system returns:

```text
No relevant match events found.
```

This is intended to prevent the generator from producing an event that does not exist in the available match data.

## Architecture

A key design decision is the separation between event extraction and the RAG pipeline.

Event extraction is implemented independently of the retrieval and question-answering components. This allows the rule-based event detection layer to be replaced by machine-learning or deep-learning event models without requiring changes to the vector indexing or answer generation components.

```text
+-----------------------------------------------------------------------------------+
|                           GAME STATE RECONSTRUCTION                               |
|                      Frame-Level Player and Ball Tracking                         |
+-----------------------------------------------------------------------------------+
                                         |

+-----------------------------------------------------------------------------------+

|                                                                                   |
| - Linear coordinate interpolation for gaps up to 8 frames                        |
| - Possession dwell-time filtering for sequences of at least 5 frames             |
| - High-press hysteresis filtering for sequences of at least 10 frames             |
+-----------------------------------------------------------------------------------+
                                         |
                                         v
+-----------------------------------------------------------------------------------+
| STAGE 2: EVENT EXTRACTION                                                         |
| src/event_extraction/heuristics.py                                                |
|                                                                                   |
| - Pitch zone mapping                                                              |
| - Defensive, midfield, and attacking thirds                                      |
| - Penalty box detection                                                           |
| - Passes, turnovers, box entries, and shots                                       |
| - Simplified offside detection                                                    |
+-----------------------------------------------------------------------------------+
                                         |
                                         v
+-----------------------------------------------------------------------------------+
| STAGE 3: EVENT-ADAPTIVE SEMANTIC CHUNKING                                         |
| src/rag/chunker.py                                                                |
|                                                                                   |
```

## Event Extraction

The event extraction layer converts frame-level tracking data into higher-level match events.

The current implementation includes:

* Pitch zone classification
* Possession estimation
* Pass detection
* Turnover detection
* Penalty box entries
* Shots on goal
* High-press sequences
* A simplified offside proxy

The extracted events are represented with timestamps and relevant metadata before being passed to the retrieval pipeline.

## Event-Adaptive Chunking

Different events require different temporal windows.

Short events such as passes, turnovers, and shots are represented using relatively small windows, typically around 3 to 6 seconds.

Continuous events such as possession spells and pressing sequences retain their natural duration, generally ranging from approximately 12 to 25 seconds.

This prevents long continuous sequences from being fragmented into multiple unrelated retrieval chunks while keeping short events sufficiently precise.

## Retrieval Pipeline

The retrieval process follows these steps:

1. Frame-level tracking data is parsed into a normalized format.
2. Tracking noise is reduced using interpolation and temporal filters.
3. Event extraction heuristics identify relevant match events.
4. Events are converted into semantic chunks.
5. Each chunk is embedded using `all-MiniLM-L6-v2`.
6. Embeddings and metadata are stored in Chroma.
7. A user query is embedded and compared against the event collection.
8. Similarity thresholds are applied to filter weak matches.
9. Relevant events are passed to the QA chain.
10. The generated response includes timestamp references.
11. FFmpeg is used to create a corresponding video segment.
12. The Streamlit application plays the retrieved portion of the match.

## Current Limitations

### 1. Simplified Offside Detection

The current offside detector is a heuristic based on the relative position of an attacker and the second-to-last defender during a forward-pass window.

It does not model the complete requirements of an official VAR decision, including:

* Exact frame selection
* Player body-part geometry
* Ball contact timing
* Precise pitch-line calibration
* Full VAR review logic

A more accurate implementation would require calibrated pitch geometry and reliable multi-camera or broadcast-to-pitch projection.

### 2. Synthetic Tracking Data

The current version operates on synthetic tracking data generated by `mock_data_gen.py`.

Real GSR output is not currently included in this repository. The GSR system responsible for player detection, ball detection, multi-object tracking, camera calibration, and jersey recognition is being developed separately.

Keeping the two systems separate avoids coupling the event retrieval project to the tracking pipeline.

The current parser provides an interface between the two systems. It converts input formats such as JSON, JSONL, or CSV into common `FrameData`, `TrackedPlayer`, and `TrackedBall` objects.

The expected real-data format is documented in:

`docs/future_work/gsr_field_mapping.md`

### 3. Difference Between Synthetic and Real Tracking Data

Synthetic trajectories are cleaner than tracking data generated from broadcast footage.

Real-world tracking systems can introduce:

* Track ID switches
* Player occlusion
* Camera motion
* Detection noise
* Incorrect jersey recognition
* Missing frames

The current preprocessing thresholds were selected for the synthetic dataset and may need to be adjusted once real GSR data is available.

The next stage is to evaluate the same pipeline using real tracking output and determine which interpolation and temporal filtering parameters require adjustment.

### 4. Rule-Based Event Detection

The current event extraction system relies on manually defined thresholds.

Examples include:

```text
Distance < 1.5 m
Speed > 3.5 m/s
```

These thresholds may behave differently depending on pitch dimensions, tracking accuracy, playing style, and match tempo.

A future version could replace selected heuristics with learned spatial-temporal models.

One possible direction is a Spatial-Temporal Graph Neural Network (ST-GNN) trained on soccer tracking datasets to classify more complex tactical events.

## Future Work

The planned improvements include:

1. Integration with real GSR tracking output.
2. Calibration of preprocessing thresholds using real match data.
3. Improved offside detection using pitch geometry.
4. More robust handling of tracking ID switches and missing detections.
5. Learned event classification using spatial-temporal models.
6. Improved retrieval for vague tactical queries.
7. Better rejection of queries with partial semantic overlap.
8. Expansion of event types beyond the current heuristic set.
9. Evaluation on larger real-world match datasets.

## Design Rationale

The system is intentionally divided into independent stages:

```text
Tracking
   ↓
Preprocessing
   ↓
Event Extraction
   ↓
Semantic Chunking
   ↓
Vector Retrieval
   ↓
Question Answering
   ↓
Video Retrieval
```

This separation makes it possible to improve individual components without redesigning the complete system.

In particular, the event extraction layer can be replaced with a learned event detection model in the future while keeping the chunking, vector database, retrieval, QA, and video playback components largely unchanged.
